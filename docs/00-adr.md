## 1. Контекст и цели

Спроектировать единый личный кабинет студента, который:

1. **Полностью исключает бумажный документооборот** — все заявления, договоры, справки рождаются, подписываются и хранятся в цифровом виде с юридической силой (ЭЦП).
2. **Автоматизирует социальные и бытовые процессы** — заселение в общежитие, льготное питание, пропускной режим (СКУД).
3. **Закрывает академические потребности** — расписание, успеваемость, GPA, транскрипты, элективы, домашние задания, тесты, апелляции, чат с преподавателями/деканатом, оплата обучения.
4. **Интегрируется с гос. базами данных РК** для автоматического получения юридически значимых сведений по ИИН.
5. **Интегрируется с LMS-системами вуза** (Platonus / 1С:Университет) как источником истины по академическим данным на переходный период.

### Ключевые не-функциональные требования
- Доступность 99.9% (SLO), деградация интеграций без потери данных (очереди + ретраи).
- Аудит каждого юридически значимого действия (подписание, выдача справки, заселение).
- Соответствие законодательству РК: ЗРК «О персональных данных и их защите» (2013), ЗРК «Об информатизации» (2015), ЗРК «Об электронном документе и электронной цифровой подписи» (2003).
- Горизонтальное масштабирование под пиковые нагрузки (начало семестра, заселение, сессия).

## 2. Границы системы и заинтересованные стороны

**Внутри системы (мы владеем):** портал + мобильное приложение + бэкенд-сервисы + шлюз интеграций + хранилище документов.

**Внешние системы (мы не владеем, только интегрируемся):**

| Система | Назначение | Протокол (ориентировочно) |
|---|---|---|
| eGov Mobile | Авторизация по QR, подписание действий | REST/QR-флоу, ЭЦП |
| NCALayer | Локальное подписание документов (ПК/моб.) | Локальный API (WebSocket/REST на localhost) |
| ЕШЭП / ШЭП | Шина электронного правительства (SOAP) | SOAP/XML + ЭЦП-подпись запросов |
| Smart Data Ukimet / Smart Bridge | Платформа обмена данными между ГБ | REST/gRPC, oAuth |
| НОБД (МП РК) | Национальная образовательная БД (контингент) | SOAP/REST |
| ГБД ФЛ (МВД), ГБД РН (адрес), МЗ (мед), МТСЗН (льготы) | Источники персональных/социальных данных | через Smart Data Ukimet |
| Platonus / 1С:Университет | LMS, академические данные | REST/SOAP/DB-адаптер |
| СКУД общежития | Пропускной режим | REST/SDK/вебхуки |
| Учётная система столовой | Синхронизация статуса льготника | REST/SDK |
| Платёжный шлюз (Halyk / eGov Pay) | Оплата обучения | REST, 3-D Secure |

> Точные эндпоинты/WSDL гос. систем получаются по договору с оператором (АО «НИТ», НУЦ, МП РК) и фиксируются в техническом паспорте интеграции. Здесь задаётся **контрактная модель** интеграционного слоя, а не жёстко прописанные URL.

**Заинтересованные стороны:** студенты, преподаватели, деканат, приёмная комиссия, бухгалтерия, юристы вуза, администрация общежития и столовой, ИТ-служба, операторы гос. систем.

## 4. Ключевые архитектурные решения

### ADR-001 — Архитектурный стиль: модульный монолит → микросервисы
**Решение:** начинаем с **модульного монолита** (единый деплоябельный артефакт, строгие границы модулей), с изоляцией интеграционных адаптеров в отдельные коннекторы. Эволюция к микросервисам — по мере роста нагрузки, но не с первого дня.
**Обоснование:** скорость вывода MVP, единая транзакционность для ЭДО-сценариев (пакетное подписание), меньше инфраструктурных затрат. Границы модулей проектируются «по швам» будущих микросервисов.
**Компромисс:** риск связанности — купируется strict modular boundaries + dependency rules.

### ADR-002 — Backend-стек
**Решение:** **NestJS (TypeScript)** для доменных сервисов; интеграционные коннекторы — лёгкие адаптеры (Node/Go) по необходимости.
**Альтернативы:** Spring Boot (Kotlin/Java) — принимается, если команда сильнее в JVM; .NET — если уже используется в вузе.
**Обоснование:** единый язык с фронтендом, быстрая итерация, зрелая экосистема (queues, OpenAPI, gRPC).

### ADR-003 — Модель обмена: REST (sync) + события (async)
**Решение:** UI → BFF → сервисы синхронно (REST/JSON, OpenAPI 3.1; gRPC — для горячих внутренних вызовов). Все межсистемные мутации (СКУД, столовая, НОБД, статусы) — **асинхронно через очередь сообщений**.
**Обоснование:** внешние системы ненадёжны и медленны; очередь даёт гарантию доставки, ретраи, DLQ, идемпотентность.

### ADR-004 — Хранилища данных
**Решение:**
- **PostgreSQL 16** — единственный источник истины (OLTP), JSONB для гибких справочников.
- **Redis** — кэш, сессии, rate limiting, краткоживущие состояния подписания.
- **MinIO (S3-совместимый)** — файлы, скан-образы, подписанные PDF.
- **OpenSearch** — поиск по документам и событиям.
- **RabbitMQ** (начало) → **Kafka** (при росте объёма событий).
**Обоснование:** реляционная целостность для ЭДО; S3 для больших бинарных объектов; вынос поиска не нагружает OLTP.

### ADR-005 — Идентификация и доступ
**Решение:** **Keycloak** как IAM (OIDC/OAuth2), JWT access-token (short-lived) + refresh. Способы входа: (1) eGov Mobile QR, (2) NCALayer/ЭЦП, (3) резервный логин/пароль для сотрудников. Роли: student, lecturer, deanery, finance, dorm_admin, canteen_admin, admin.
**Обоснование:** проверенный OIDC-провайдер, федерация внешних IdP, аудит сессий.

### ADR-006 — ЭЦП и ЭДО
**Решение:** отдельный **Signature Service**:
- Пользовательское подписание → через **NCALayer** (локальный агент) или eGov Mobile (QR).
- Вузовское подписание (справки, договоры) → **серверная ЭЦП вуза** (HSM / защищённое хранилище ключей).
- Форматы: **CAdES (PKCS#7/CMS)** для документов, **XAdES/XML DSig** для гос. SOAP-запросов, **PAdES** для PDF.
- Проверка: OCSP/CRL НУЦ РК, цепочка доверия к сертификатам.
- Каждый документ получает **hash-chain** (цепочку хэшей) для гарантии целостности архива.
**Обоснование:** ЭЦП — ядро юридической значимости; изоляция в отдельный сервис упрощает сертификацию и смену провайдера.

### ADR-007 — Интеграционный слой
**Решение:** **Integration Hub** с адаптерами per-система + унифицированная модель входящих/исходящих сообщений. Паттерны: **Outbox + idempotency-key**, ретраи с экспоненциальной паузой, **DLQ**, версионирование API. Все гос. запросы подписываются ЭЦП и логируются (аудит).
**Обоснование:** внешние интеграции — главный источник нестабильности; их изоляция критична.

### ADR-008 — Безопасность и соответствие
**Решение:** zero-trust на периметре, шифрование in-transit (TLS 1.3) и at-rest (AES-256), маскирование ПДн в логах, полный аудит-трейл, разделение сред (dev/stage/prod), SIEM-сбор. Хранение персональных данных — на серверах в РК (либо с контролируемым согласием), DPA-соглашения.
**Обоснование:** работа с ПДн и гос. интеграциями налагает жёсткие требования регуляторов.

### ADR-009 — Фронтенд
**Решение:** **Web SPA/PWA — React + TypeScript + Next.js**; мобильное приложение — **React Native** (или Flutter, если нужна единая кодовая база с iOS/Android). UI-кит: дизайн-система вуза.
**Обоснование:** eGov Mobile-подобный UX, офлайн-кэш расписания, PWA как резервный канал.

### ADR-010 — Деплой и наблюдаемость
**Решение:** **Kubernetes** (облако РК / on-prem), GitOps (ArgoCD), CI/CD (GitHub/GitLab Actions), **OpenTelemetry** → Grafana + Loki + Prometheus + Tempo. IaC (Terraform).
**Обоснование:** воспроизводимость, горизонтальное масштабирование, единая наблюдаемость.

## 5. Целевая архитектура (C4 Level 1–2, описание)

```
[Студент/Преподаватель/Сотрудник]
      │ Web PWA / Mobile
      ▼
[API Gateway / BFF] ── (JWT) ── [Keycloak IAM]
      │
      ├── IAM & Profile ───────────┐
      ├── Academic (LMS) ──────────┤
      ├── Accommodation ───────────┤── [PostgreSQL] [Redis] [MinIO] [OpenSearch]
      ├── Social Benefits ─────────┤
      ├── University Services ─────┤
      ├── Document & Signature ────┤
      │        │
      │        ├── NCALayer (local) / eGov Mobile QR
      │        └── HSM (вуз ЭЦП)
      │
      └── Integration Hub ──► ЕШЭП/Smart Data Ukimet/НОБД/Platonus/1С/СКУД/Столовая/Платёж
                     │
                     └── [RabbitMQ/Kafka] ── [Notification] ──► E-mail/SMS/Push
```

> Полные C4-диаграммы (Context / Container / Component, PlantUML + Mermaid) и sequence-диаграммы ключевых сценариев — в `01-architecture.md`.

## 9. Открытые вопросы и риски

1. **Доступ к тестовым контурам гос. систем** — критический путь; без договоров невозможна сквозная интеграция.
2. **Выбор LMS как источника истины** — на переходный период Platonus/1С остаётся мастером данных по оценкам; нужна стратегия миграции «в обратную сторону».
3. **Серверная ЭЦП вуза** — требуется HSM или защищённое хранилище; процедура закупки/сертификации.
4. **Согласие на обработку ПДн** — UX-флоу согласия при первом входе (юридическая обязательность).
5. **Нагрузка при заселении/сессии** — необходимо нагрузочное тестирование интеграционных сценариев.
6. **Точный формат ЕШЭП/НОБД** — уточняется по техпаспорту оператора; в спеку закладываем контрактную модель с версионированием.

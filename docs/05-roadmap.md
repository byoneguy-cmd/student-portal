## 1. Общая стратегия и принципы поставки

### 1.1. Стратегические принципы

1. **MVP-первым (value-first).** Каждый релиз приносит студенту измеримую ценность: сначала — войти и увидеть расписание/оценки (Фаза 1), затем — заселиться без бумаги (Фаза 2), затем — льготное питание (Фаза 3), затем — полный академический цикл и услуги (Фаза 4). Никакого «биг-бэнг» релиза.
2. **Инкрементальность и обратимость.** Каждый спринт заканчивается работающим инкрементом, который можно показать пилотной группе. Релизы — через canary и feature flags (раздел 10), откат — автоматизированный.
3. **Контракты гос. интеграций — критический путь.** Все сценарии, зависящие от ЕШЭП/Smart Data Ukimet, НОБД, eGov Mobile и НУЦ, нельзя реализовать до подписания договоров и получения тестовых контуров. Поэтому Фаза 0 запускается немедленно и параллельно с Фазой 1; работы, не зависящие от гос. контуров, не блокируются (см. раздел 3, карту блокировок).
4. **Контрактная модель интеграций.** Точные WSDL/эндпоинты фиксируются в техническом паспорте оператора; до этого код пишется против версионируемых контрактных интерфейсов и моков (порт-адаптерная архитектура, ADR-007). Переключение с мока на реальный контур — только сменой адаптера.
5. **Модульный монолит сейчас, микросервисы позже (ADR-001).** Границы модулей проектируются «по швам» будущих микросервисов с самого первого спринта.
6. **Юридическая значимость — сквозное требование.** ЭЦП (ADR-006) и аудит (ADR-008) встроены в определение готовности, а не «доделываются потом».
7. **Наблюдаемость и безопасность — с нуля (ADR-010, ADR-008).** SLO 99.9%, трассировка, аудит-лог, разделение сред dev/stage/prod закладываются в Фазе 0, а не в конце.
8. **Пилотная группа с ранних фаз.** Фаза 1 завершается закрытым бета-доступом для 1–2 факультетов; заселение (Фаза 2) — пилот на одном общежитии.

### 1.2. Каденция и ритм поставки

- **Спринт = 2 недели.** Демо в конце каждого спринта перед заказчиком (проректор по цифровизации, деканат, ИТ-служба).
- **Релизный поезд:** web/back — каждый спринт в stage; в prod — по вехам фаз (см. раздел 8).
- **Определение готовности (Definition of Ready):** история принята только при наличии acceptance criteria, оценке, указанных зависимостей и владельца.
- **Единый Definition of Done** — см. раздел 3.0.

### 1.3. Критический путь (сводно)

```
Договоры НИТ/НУЦ/МП РК  ──►  Тестовые контуры + техпаспорта  ──►  Реальные адаптеры
        │                                                              │
        │   блокирует: импорт по ИИН (1.3), льготы (3.1),              │
        │             справки (4.1), НОБД-контингент (1.4)             │
        └──► HSM / серверная ЭЦП вуза  ──►  договоры найма (2.3), справки (4.1)
```

Детальная карта блокировок — в конце раздела 3.

## 3. Детальная разбивка по спринтам

### 3.0. Сквозные артефакты и общий Definition of Done

**Сквозные артефакты (создаются/уточняются по мере фаз):**
- Контрактный реестр интеграций (техпаспорта) — `03-integrations-kz.md`.
- ERD и DDL — `02-database.md`.
- C4-диаграммы — `01-architecture.md`.
- Стек и безопасность — `04-stack-and-security.md`.
- Тестовые данные (синтетические ИИН, тестовые ЭЦП НУЦ, моки LMS).

**Общий Definition of Done (применяется ко всем историям всех спринтов; спринтовый DoD добавляет специфику):**
- [ ] Код прошёл ревью (минимум 1 аппрув, для модулей ЭДО/IAM — 2).
- [ ] Юнит-тесты покрывают новую бизнес-логику (целевое покрытие ≥ 70% на модуль).
- [ ] Автотесты API (интеграционные) зелёные в CI; для критических сценариев — контрактные тесты.
- [ ] OpenAPI-спецификация обновлена и сгенерированы клиенты.
- [ ] Миграции БД — idempotent, с rollback-сценарием.
- [ ] Аудит-событие для каждого юридически значимого действия логируется (кто/что/когда/по какому ИИН/результат).
- [ ] Логи не содержат ПДн в открытом виде (маскирование, ADR-008).
- [ ] Наблюдаемость: метрики RED (rate/error/duration) и трассировка по новому пути.
- [ ] Документация (ADR/README/runbook) обновлена.
- [ ] Приёмка заказчиком на демо-стенде (для историй уровня epic).

**Формат ролей:** `student`, `lecturer`, `deanery`, `finance`, `dorm_admin`, `canteen_admin`, `admin`, `integration_engineer`, `compliance_officer` (см. ADR-005).

### Фаза 0 — Discovery

> Фаза 0 частично параллельна Фазе 1: контрактные и инфраструктурные работы идут одновременно с разработкой каркаса платформы. Без завершения контрактного трека блокируются только «реальные адаптеры» (S1.3, S1.4 и далее).

#### Спринт 0.1 — Организационное закрепление и контрактный контур

**Цель спринта.** Запустить договорной процесс с операторами (НИТ, НУЦ, МП РК, вуз), зафиксировать зоны ответственности и сформировать реестр контактов/рисков.

**Эпики и user stories:**
- **Эп. 0.1-E1. Договорной контур.** Как *compliance_officer*, я хочу реестр договоров и их статусов (инициация → согласование → подписание → активация тестового контура), чтобы видеть блокирующие зависимости проекта.
- **Эп. 0.1-E2. Юридическая проработка.** Как *compliance_officer*, я хочу шаблоны NDA, DPA (обработка ПДн) и соглашения об уровне обслуживания с операторами, чтобы соответствовать ЗРК «О персональных данных» и «Об информатизации».
- **Эп. 0.1-E3. Реестр заинтересованных сторон.** Как *PM*, я хочу матрицу RACI по каждой интеграции и списки ответственных с обеих сторон, чтобы каждый вопрос решался без поиска «кто отвечает».

**Acceptance criteria:**
- Given реестр договоров создан, When PM открывает его, Then каждая интеграция (НИТ/НУЦ/МП РК/eGov Mobile/LMS/СКУД/столовая/платёж) имеет статус и ответственного с датой актуализации.
- Given шаблон DPA, When юрист проверяет, Then он содержит пункты о целях обработки, сроках, праве на отзыв согласия и локализации ПДн в РК.
- Given матрица RACI, When возникает вопрос по ЕШЭП, Then в матрице есть исполнитель и эскалатор не позже 24 ч.

**Definition of Done (специфика):** реестр договоров заведён в трекер с автоматическим напоминанием; шаблоны NDA/DPA согласованы юрслужбой; RACI утверждён.

**Deliverables:** реестр договоров и контактов; шаблоны NDA/DPA/SLA; матрица RACI; карта рисков интеграций (связь с разделом 6).

**Зависимости:** нет (внешних блокеров нет; зависит только от воли вуза).

#### Спринт 0.2 — Технические паспорта и тестовые контуры

**Цель спринта.** Получить технические паспорта интеграций и доступы к тестовым контурам (sandbox) для ЕШЭП, Smart Data Ukimet, НОБД, eGov Mobile, NCALayer; зафиксировать контракты.

**Эпики и user stories:**
- **Эп. 0.2-E1. Техпаспорта.** Как *integration_engineer*, я хочу техпаспорт с WSDL/эндпоинтами, схемами запросов/ответов, правилами подписи и лимитами, чтобы строить адаптеры по контракту.
- **Эп. 0.2-E2. Тестовые контуры.** Как *integration_engineer*, я хочу доступы (тестовые ЭЦП, сертификаты, VPN/брандмауэрные правила) к sandbox-средам, чтобы проверять запросы без боевых данных.
- **Эп. 0.2-E3. Контрактная спецификация.** Как *tech_lead*, я хочу версионируемый контракт на каждый интеграционный поток (JSON Schema / WSDL / OpenAPI), чтобы команды могли разрабатывать на моках параллельно.

**Acceptance criteria:**
- Given техпаспорт ЕШЭП, When интеграционист разворачивает sandbox, Then успешный SOAP-запрос «получить данные по ИИН» с тестовой ЭЦП возвращает валидный XML.
- Given контракт, When разработчик меняет поле ответа, Then схема версионируется (semver) и CI падает при нарушении обратной совместимости.
- Given sandbox НОБД, When отправлен тестовый ИИН, Then возвращается контингент (или документированный код «не найден»).

**Definition of Done (специфика):** каждый паспорт загружен в репозиторий `docs/03-integrations-kz.md`; sandbox-креденшелы хранятся в секрет-менеджере (не в git); smoke-запросы задокументированы в Postman/Bruno-коллекции.

**Deliverables:** технические паспорта; доступы к sandbox; версионируемые контракты; коллекции smoke-запросов.

**Зависимости:** **блокируется** договорами (спринт 0.1). Критический путь.

#### Спринт 0.3 — Инфраструктура и CI/CD

**Цель спринта.** Поднять базовую инфраструктуру dev и пайплайны CI/CD (GitOps), чтобы каждая последующая история проходила автоматическую сборку и развёртывание.

**Эпики и user stories:**
- **Эп. 0.3-E1. Кластер и окружения.** Как *devops*, я хочу Kubernetes-кластер с разделением dev/stage/prod и namespace per окружение, чтобы изолировать среды.
- **Эп. 0.3-E2. Базовые сервисы.** Как *devops*, я хочу развёрнутые PostgreSQL 16, Redis, MinIO, OpenSearch, RabbitMQ, Keycloak в dev через IaC (Terraform/Helm), чтобы команды не блокировались на ручном развёртывании.
- **Эп. 0.3-E3. CI/CD и GitOps.** Как *devops*, я хочу пайплайны сборки, тестов, сканирования (SAST/DAST, зависимостей) и ArgoCD-синхронизации, чтобы каждая поставка была воспроизводимой.
- **Эп. 0.3-E4. Наблюдаемость-каркас.** Как *SRE*, я хочу Grafana + Prometheus + Loki + Tempo с базовыми дашбордами RED, чтобы видеть состояние сервисов с первого дня.

**Acceptance criteria:**
- Given пустой git-репозиторий, When разработчик пушит в main, Then пайплайн собирает, прогоняет тесты и деплоит в dev за ≤ 15 минут.
- Given контейнер-образ, When сканируется, Then блокируются critical/high уязвимости (policy gate).
- Given метрики RED, When SRE открывает дашборд, Then видны rate/error/duration по ключевым сервисам.
- Given секрет, When проверяется git, Then в репозитории нет секретов (secret scanning включён).

**Definition of Done (специфика):** dev-среда разворачивается «с нуля» за ≤ 1 ч по runbook; IaC в git; каждый релиз имеет понятный rollback (ArgoCD revision).

**Deliverables:** K8s-кластер(ы) dev, базовые сервисы, CI/CD, GitOps, наблюдаемость-каркас, runbook развёртывания.

**Зависимости:** частично параллельно 0.1/0.2; не блокируется гос. контурами.

### Фаза 1 — MVP Academic + IAM

#### Спринт 1.1 — Каркас платформы и модульного монолита

**Цель спринта.** Создать NestJS-модульный монолит со строгими границами модулей (ADR-001), BFF/API Gateway и сквозную аутентификацию по JWT.

**Эпики и user stories:**
- **Эп. 1.1-E1. Скелет монолита.** Как *backend*, я хочу NestJS-приложение с модулями (iam, document, accommodation, social, academic, services, integration-hub, notification, ops) и dependency rules, чтобы границы модулей были «швами» будущих микросервисов.
- **Эп. 1.1-E2. BFF/Gateway.** Как *backend*, я хочу API Gateway с маршрутизацией, rate limiting и валидацией JWT на периметре, чтобы все UI-запросы проходили единую точку.
- **Эп. 1.1-E3. Персистентность.** Как *backend*, я хочу схемы БД (ключевые сущности `users`, `profiles`, `students`, `enrollments`) с миграциями и JSONB-справочниками, чтобы данные хранились целостно.
- **Эп. 1.1-E4. Моки интеграций.** Как *integration_engineer*, я хочу порт-адаптеры с моками для всех внешних систем, чтобы разработка шла без реальных контуров.

**Acceptance criteria:**
- Given модуль A, When он обращается к модулю B, Then только через публичный интерфейс (запрет прямого импорта внутренностей; проверяется архитектурным тестом/ESLint-boundaries).
- Given JWT без/с истёкшим сроком, When запрос к Gateway, Then 401/403 без доступа к downstream-сервисам.
- Given превышение лимита, When клиент шлёт N+1 запрос/сек, Then Gateway возвращает 429.
- Given миграция, When применяется повторно, Then идемпотентна (no-op).

**Definition of Done (специфика):** архитектурный тест границ модулей в CI; OpenAPI сгенерирован; каркас деплоится в dev.

**Deliverables:** скелет монолита, Gateway, миграции, моки-адаптеры, OpenAPI.

**Зависимости:** инфраструктура (0.3). Гос. контуры — не требуется (работа на моках).

#### Спринт 1.2 — IAM: Keycloak + вход eGov QR и NCALayer

**Цель спринта.** Реализовать аутентификацию студентов через eGov Mobile QR и NCALayer (ЭЦП), с Keycloak как OIDC-провайдером.

**Эпики и user stories:**
- **Эп. 1.2-E1. OIDC и сессии.** Как *student*, я хочу входить через Keycloak (OIDC) с короткоживущим access-token и refresh, чтобы сессии были безопасными и управляемыми.
- **Эп. 1.2-E2. Вход eGov Mobile QR.** Как *student*, я хочу отсканировать QR и подтвердить вход в eGov Mobile, чтобы не вводить пароль.
- **Эп. 1.2-E3. Вход NCALayer.** Как *student*, я хочу подписать challenge своим ключом ЭЦП через NCALayer, чтобы войти с полной юридической значимостью.
- **Эп. 1.2-E4. Резервный вход сотрудников.** Как *admin*, я хочу логин/пароль + MFA для сотрудников вуза, чтобы был отказоустойчивый канал входа.
- **Эп. 1.2-E5. Роли и согласие.** Как *student*, я хочу при первом входе дать согласие на обработку ПДн (обязательный UX-флоу), чтобы вуз соответствовал закону.

**Acceptance criteria:**
- Given QR-флоу, When студент подтверждает в eGov Mobile, Then сервер получает валидный ИИН и выдаёт JWT; при неверном подтверждении — отказ с аудитом.
- Given NCALayer, When студент подписывает challenge, Then подпись валидируется по OCSP/CRL НУЦ (цепочка доверия) и выдаётся JWT.
- Given истёкший refresh-token, When клиент пытается продлить сессию, Then 401 и принудительный повторный вход.
- Given первый вход, When студент не дал согласие, Then доступ к данным профиля заблокирован до согласия; согласие фиксируется в аудите (версионируемо).
- Given роль `student`, When запрос к admin-эндпоинту, Then 403.

**Definition of Done (специфика):** OIDC-конфигурация в Keycloak зафиксирована в IaC; флоу согласия протестирован юрслужбой; аудит входов пишется.

**Deliverables:** аутентификация eGov QR + NCALayer + резервный вход; флоу согласия; роли в Keycloak.

**Зависимости:** **критический путь** — sandbox eGov Mobile и NCALayer (спринт 0.2, оператор НИТ/МЦРИАП) и OCSP/CRL НУЦ. До получения контуров реализуется на моках, но «реальная приёмка» блокируется.

#### Спринт 1.3 — Профиль по ИИН (импорт из Smart Data Ukimet)

**Цель спринта.** Реализовать импорт и формирование профиля студента по ИИН из государственных баз через Integration Hub.

**Эпики и user stories:**
- **Эп. 1.3-E1. Импорт ФЛ.** Как *student*, я хочу, чтобы мои ФИО, дата рождения, адрес подтягивались по ИИН, чтобы не заполнять вручную.
- **Эп. 1.3-E2. Integration Hub core.** Как *integration_engineer*, я хочу Outbox + idempotency-key + ретраи с экспоненциальной паузой + DLQ (ADR-007), чтобы внешние вызовы были надёжными.
- **Эп. 1.3-E3. Аудит импорта.** Как *compliance_officer*, я хочу, чтобы каждый импорт по ИИН логировался (источник, цель, результат), чтобы был полный аудит-трейл.

**Acceptance criteria:**
- Given валидный ИИН, When студент входит, Then профиль создаётся/обновляется из Smart Data Ukimet; конфликтующие данные помечаются и не перезаписываются молча.
- Given сбой внешнего контура, When запрос падает, Then сообщение уходит в ретраи (экспоненциально, до N попыток) и затем в DLQ; повторная доставка идемпотентна (одинаковый idempotency-key → один результат).

**Зависимости:** 3.1–3.2; готовность столовой.

### Фаза 4 — Услуги + глубокая интеграция LMS

#### Спринт 4.1 — Справки с места учёбы (серверная ЭЦП вуза)

**Цель спринта.** Реализовать выдачу справок с места учёбы, подписанных серверной ЭЦП вуза, с полным аудитом.

**Эпики и user stories:**
- **Эп. 4.1-E1. Заказ справки.** Как *student*, я хочу заказать справку (о обучении, о статусе студента) онлайн, чтобы не идти в деканат.
- **Эп. 4.1-E2. Подписание ЭЦП вуза.** Как *backend*, я хочу автоматически подписывать справку серверной ЭЦП вуза (PAdES), чтобы она была юридически значимой.
- **Эп. 4.1-E3. Статусы и выдача.** Как *student*, я хочу отслеживать статус справки (заказана → подписана → готова) и скачать её, чтобы контролировать процесс.

**Acceptance criteria:**
- Given заказ справки, When студент оформляет, Then справка формируется из данных (НОБД/профиль) и подписывается ЭЦП вуза за ≤ X минут (SLA).
- Given скачанная справка, When проверяется, Then PAdES-подпись валидна (верифицируется НУЦ), целостность подтверждена.
- Given заказ, When студент открывает, Then видит статус и историю (аудит выдачи).

**Definition of Done (специфика):** справка верифицируется внешним сервисом НУЦ; аудит выдачи полный; выдача возможна только при валидном контингенте (НОБД).

**Deliverables:** сервис справок, автоподписание ЭЦП вуза, статусы/скачивание.

**Зависимости:** **критический путь** — HSM (2.3) и sandbox НОБД (0.2). Без них выдача юридически значимых справок блокируется.

#### Спринт 4.2 — Оплата обучения (платёжный шлюз)

**Цель спринта.** Реализовать баланс и оплату обучения через платёжный шлюз (Halyk/eGov Pay, 3-D Secure).

**Эпики и user stories:**
- **Эп. 4.2-E1. Баланс.** Как *student*, я хочу видеть баланс и начисления по обучению, чтобы понимать задолженность.
- **Эп. 4.2-E2. Оплата.** Как *student*, я хочу оплатить обучение онлайн (карта/перевод) с 3-D Secure, чтобы не идти в кассу.
- **Эп. 4.2-E3. Сверка платежей.** Как *finance*, я хочу автоматическую сверку платежей (callback + reconcile), чтобы начисления были точными.

**Acceptance criteria:**
- Given начисления, When студент открывает баланс, Then суммы и периоды соответствуют данным бухгалтерии.
- Given оплата, When проходит 3-D Secure и возвращает success-колбэк, Then баланс обновляется; при рассинхронизации колбэка — reconcile восстанавливает состояние.
- Given оплата, When идемпотентный повтор колбэка, Then двойного зачисления не происходит (idempotency-key).

**Definition of Done (специфика):** PCI-требования соблюдены (карты не хранятся; только токенизация шлюза); тесты на тестовых картах шлюза.

**Deliverables:** баланс, оплата, сверка платежей.

**Зависимости:** sandbox платёжного шлюза (договор с банком); интеграция с учётной системой вуза.

#### Спринт 4.3 — Элективы, домашние задания, тесты

**Цель спринта.** Углубить LMS-интеграцию: элективы, домашние задания, онлайн-тесты.

**Эпики и user stories:**
- **Эп. 4.3-E1. Элективы.** Как *student*, я хочу записаться на элективные дисциплины онлайн, чтобы выбрать курсы без деканата.
- **Эп. 4.3-E2. Домашние задания.** Как *student*, я хочу сдавать ДЗ и видеть дедлайны/оценки, чтобы не пропускать сроки.
- **Эп. 4.3-E3. Тесты.** Как *student*, я хочу проходить онлайн-тесты с ограничением времени, чтобы аттестовываться дистанционно.
- **Эп. 4.3-E4. Роль преподавателя.** Как *lecturer*, я хочу публиковать задания/тесты и выставлять оценки, чтобы вести курс онлайн.

**Acceptance criteria:**
- Given электив, When студент записывается, Then запись проходит с проверкой лимита мест и пререквизитов; конфликт расписания детектируется.
- Given ДЗ, When студент сдаёт до дедлайна, Then фиксируется timestamp сдачи; после дедлайна — политика (поздняя сдача/отказ) применяется.
- Given тест, When таймер истёк, Then ответы отправляются автоматически; результаты сохраняются.
- Given оценка, When lecturer выставляет, Then синхронизируется с журналом/GPA (обратная запись в LMS при необходимости).

**Definition of Done (специфика):** стратегия записи в LMS (write-back) для оценок/элективов согласована; тесты устойчивы к обрыву сети.

**Deliverables:** элективы, ДЗ, тесты, роль преподавателя.

**Зависимости:** **критический путь** — расширенный API LMS (запись, а не только чтение); соглашение с вендором/ИТ-службой вуза.

#### Спринт 4.4 — Апелляции и чат с преподавателями/деканатом

**Цель спринта.** Реализовать апелляции по оценкам и встроенный чат (преподаватель/деканат).

**Эпики и user stories:**
- **Эп. 4.4-E1. Апелляция.** Как *student*, я хочу подать апелляцию по оценке с приложением обоснования, чтобы оспорить результат в срок.
- **Эп. 4.4-E2. Рассмотрение.** Как *deanery*, я хочу маршрутизировать апелляции в комиссию и фиксировать решение, чтобы процесс был прозрачным.
- **Эп. 4.4-E3. Чат.** Как *student*, я хочу переписываться с преподавателем/деканатом внутри приложения, чтобы решать вопросы без личного визита.

**Acceptance criteria:**
- Given апелляция, When студент подаёт в срок (регламентный), Then заявка зарегистрирована с таймером SLA и уведомлением комиссии.
- Given решение комиссии, When внесено, Then студент получает уведомление, решение фиксируется в аудите и (при изменении) в журнале.
- Given чат, When отправлено сообщение, Then доставлено с read-статусом; история хранится с аудитом доступа.

**Definition of Done (специфика):** регламент апелляций (сроки) конфигурируем; чат — через очередь/сокеты с гарантией доставки.

**Deliverables:** апелляции, чат, уведомления.

**Зависимости:** 4.3 (журнал/оценки); регламенты деканата.

#### Спринт 4.5 — Полный академический цикл, приёмка

**Цель спринта.** Замкнуть полный академический цикл (расписание → ДЗ → тесты → оценки → апелляции → транскрипт/справки) и провести приёмку.

**Эпики и user stories:**
- **Эп. 4.5-E1. Сквозной сценарий.** Как *student*, я хочу пройти весь академический цикл онлайн, чтобы минимизировать очные визиты.
- **Эп. 4.5-E2. Приёмка.** Как *PM*, я хочу демо полного цикла перед заказчиком, чтобы получить решение о переходе к Hardening.
- **Эп. 4.5-E3. Закрытие дефектов.** Как *QA*, я хочу регресс по всем модулям, чтобы система была стабильна перед нагрузкой.

**Acceptance criteria:**
- Given полный цикл, When студент проходит, Then все операции выполняются без бумаги и с аудитом.
- Given приёмка, When проведена, Then критерии по KPI фазы 4 выполнены (раздел 7).
- Given дефект, When закрытие, Then 0 critical, ≤ 3% high с планом.

**Definition of Done (специфика):** go/no-go решение на Hardening задокументировано.

**Deliverables:** полный академический цикл, приёмочный протокол.

**Зависимости:** 4.1–4.4.

### Фаза 5 — Hardening / релиз

#### Спринт 5.1 — Мобильное приложение (React Native) и PWA

**Цель спринта.** Выпустить мобильное приложение (iOS/Android) с ключевыми сценариями и доработать PWA как резервный канал.

**Эпики и user stories:**
- **Эп. 5.1-E1. Мобильное ядро.** Как *student*, я хочу мобильное приложение с профилем, расписанием, журналом, заселением, питанием и справками, чтобы пользоваться с телефона.
- **Эп. 5.1-E2. Push-уведомления.** Как *student*, я хочу push-уведомления (дедлайны, статусы, чат), чтобы не пропускать события.
- **Эп. 5.1-E3. PWA-резерв.** Как *student*, я хочу устанавливаемый PWA с офлайн-расписанием, чтобы иметь резервный канал без магазинов.

**Acceptance criteria:**
- Given мобильное приложение, When студент входит, Then ключевые сценарии работают на iOS и Android (паритет функций с web для core-флоу).
- Given push, When событие возникает, Then уведомление доставлено ≤ 30 с (p95) с корректной deeplink-навигацией.
- Given PWA, When сеть отсутствует, Then расписание доступно офлайн.

**Definition of Done (специфика):** сборки в App Store/Google Play (или Enterprise-распространение); E2E на эмуляторах в CI.

**Deliverables:** мобильное приложение, push, PWA.

**Зависимости:** все модули фаз 1–4; сертификаты магазинов приложений.

#### Спринт 5.2 — Наблюдаемость, нагрузочное тестирование, аудит безопасности

**Цель спринта.** Довести наблюдаемость, пройти нагрузочное тестирование пиковых сценариев и аудит безопасности/соответствия.

**Эпики и user stories:**
- **Эп. 5.2-E1. Наблюдаемость полная.** Как *SRE*, я хочу SLO-дашборды, алертинг и трассировку по всем сервисам, чтобы оперативно реагировать на инциденты.
- **Эп. 5.2-E2. Нагрузочное тестирование.** Как *SRE*, я хочу нагрузочные тесты сценариев заселения/сессии/оплаты, чтобы подтвердить масштабируемость.
- **Эп. 5.2-E3. Аудит безопасности.** Как *security*, я хочу pentest, аудит соответствия (ПДн, информатизация) и закрытие находок, чтобы пройти регуляторные требования.
- **Эп. 5.2-E4. DR и бэкапы.** Как *SRE*, я хочу сценарии восстановления (RPO/RTO) и резервное копирование, чтобы гарантировать непрерывность.

**Acceptance criteria:**
- Given SLO 99.9%, When замерен за период, Then фактическая доступность ≥ 99.9% (в stage-прогоне).
- Given нагрузочный тест, When пик × 1.3 (заселение/сессия), Then p95 ≤ целевого и 0 критических ошибок; выявлены и устранены узкие места.
- Given pentest, When завершён, Then все critical/high находки закрыты или принят риск (с подписью владельца).
- Given DR-тест, When выполнен, Then восстановление укладывается в RPO/RTO (задокументированные).

**Definition of Done (специфика):** отчёты нагрузочного теста и pentest подписаны; SLO-алерты включены; runbook инцидентов готов.

**Deliverables:** полная наблюдаемость, отчёты нагрузки/pentest, DR-план, runbook.

**Зависимости:** 5.1 (мобильное для нагрузки); гос. контуры для реалистичной нагрузки.

#### Спринт 5.3 — Production go-live, canary, гиперуход (hypercare)

**Цель спринта.** Выполнить поэтапный production-релиз (canary → полный трафик), обеспечить гиперуход и зафиксировать переход в эксплуатацию.

**Эпики и user stories:**
- **Эп. 5.3-E1. Canary-выкатка.** Как *SRE*, я хочу canary-деплой (5% → 25% → 100%) с автоматическим откатом по метрикам, чтобы минимизировать риск.
- **Эп. 5.3-E2. Feature flags.** Как *PM*, я хочу управлять фичами через feature flags, чтобы отключать проблемные функции без релиза.
- **Эп. 5.3-E3. Hypercare.** Как *SRE*, я хочу усиленное дежурство 24/7 в первые 2 недели, чтобы быстро закрывать инциденты.
- **Эп. 5.3-E4. Переход в эксплуатацию.** Как *PM*, я хочу передать систему в эксплуатацию с runbook и SLA, чтобы завершить проект.

**Acceptance criteria:**
- Given canary 5%, When метрики ошибок растут выше порога, Then автоматический откат на предыдущую версию ≤ 5 минут.
- Given feature flag, When выключен, Then фича недоступна пользователям без деплоя.
- Given инцидент, When в hypercare, Then время реакции ≤ 15 минут, документирован post-mortem.
- Given передача, When завершена, Then все runbook, SLA и зоны ответственности переданы ИТ-службе.

**Definition of Done (специфика):** go-live отчёт; пост-релизный NPS; инциденты закрыты; эксплуатационная документация подписана.

**Deliverables:** production-релиз, canary/feature flags, hypercare-отчёт, акт передачи.

**Зависимости:** 5.1–5.2; готовность продуктива и операторов.

## 10. План релизов и выкатки

### 10.1. Стратегия релизов

- **Релизный поезд:** web/backend — в stage каждый спринт; в prod — по вехам фаз (M1–M5), с согласия gate-review.
- **Три среды:** dev (каждый merge) → stage (каждый спринт) → prod (по вехе). Гос. интеграции в stage/prod — только против реальных контуров (или явно помеченных моков в dev).
- **Версионирование:** семантическое (semver); миграции БД — обратимые (up/down).

### 10.2. Canary-выкатка

```
100% старый ──► 95% старый / 5% canary ──► 75/25 ──► 100% новый
                       │
                (метрики ошибок/латентности растут → автооткат ≤ 5 мин)
```
- **Пороги:** рост 5xx > порог, рост p95 > порог, падение успешности подписания — триггеры автоматического отката (ArgoCD revision rollback).
- **Наблюдение:** минимум 30 минут на каждом шаге canary; для критических сценариев (ЭЦП, оплата) — отдельные дашборды.

### 10.3. Feature flags

- Все новые фичи (после MVP) выкатываются под feature flags; включение — по когортам (пилотная группа → факультет → все).
- Используются для kill-switch проблемных функций (например, отключение конкретного гос. адаптера без остановки системы).
- Правила: у каждого флага — владелец, срок жизни, критерий «уборки» (cleanup) после стабилизации.

### 10.4. Откат

- **Уровень кода:** ArgoCD откат на предыдущую ревизию (≤ 5 мин), триггерится вручную или автоматически по SLO-алертам.
- **Уровень данных:** миграции БД — обратимые; откат данных — по сценарию (backfill/rollback-скрипты, проверенные в stage).
- **Уровень интеграций:** при деградации внешнего контура — переключение в «degraded mode» (данные из кэша/последнего известного состояния + очередь наверстывания), без потери данных (ADR-003).
- **Критерии аварийного отката:** критический инцидент, нарушающий SLO или юридическую значимость, — немедленный rollback с post-mortem в течение 24 ч.
